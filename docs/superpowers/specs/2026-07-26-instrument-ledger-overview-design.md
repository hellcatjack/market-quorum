# 标的台账与预测表现总览设计

## 目标

将当前以单次评估任务为中心的总览页升级为以标的为中心的研究台账，让多人使用时能够快速回答：系统正在研究哪些标的、最新有效判断是什么、判断之后实际表现如何、同一标的的观点如何变化、哪些运行异常需要处理。

本功能只修改 MarketQuorum 平台层，不修改 TradingAgents。

## 现状与问题

当前总览页直接展示评估任务，每次运行占一行。重复评估会挤占页面空间，也会把有效结论、技术重试、失败记录和取消记录放在同一层级。现有标的历史页虽然可以按 ticker 查询历次评估，但仍是一张任务表，后端 `validation_outcome` 尚未绑定实际验证结果。

当前数据中共有 62 次评估、38 个标的；NVDA 单独占 20 次。默认继续按任务排列已经不能有效表达研究结论。

## 信息架构

总览页保留一套筛选条件，但提供两个明确视图：

1. **标的台账**：默认视图。每个规范化标的一行，面向研究、决策和复盘。
2. **任务记录**：次级视图。保留现有逐任务列表，面向排队、失败处理和运行监控。

页面顶部的容量、排队、运行中、异常和数据源熔断信息保持全局可见。任务异常不得因为标的折叠而隐藏。

## 标的台账行

每行展示：

- 中文名称、ticker、交易所和资产类型；
- 最新成功评估的评级、分析日期和摘要；
- 最新运行状态；如果最新运行失败，仍保留最近一次成功结论并单独显示异常；
- 默认 20 个交易日的预测—表现配对；20 日未完成时退回最长已完成周期，并明确标注周期；
- 标的总回报、基准 Alpha、方向正确性和目标价状态；
- 同周期历史已成熟样本数、方向命中数和命中率；样本少于 3 次时显示“样本不足”，不下稳定性结论；
- 最新评级相对于上一次成功评级的变化；
- 成功、运行中、排队、失败/需处理的评估数量。

预测与表现必须绑定成单一阅读单元，例如：

```text
Underweight ↓ → 20D -20.65% / Alpha -14.59% → 方向正确
```

评级颜色和验证正确性使用两套独立视觉编码，不能只依赖红绿颜色传达含义。

点击标的主体进入标的历史页；点击最新结论或异常计数进入对应评估详情。

## 归拢规则

1. 按数据库中的规范化标的身份归拢，不在浏览器中仅按 ticker 文本猜测身份。
2. 最新有效结论取最新一条 `succeeded` 且存在 Decision 的评估。
3. 最新运行状态取该标的创建时间最新的评估，不覆盖最新有效结论。
4. 可靠性统计只使用 `completed` 的验证，不纳入 scheduled、failed、unavailable、cancelled 或被隔离的评估。
5. 同一次请求的重试通过 request ID 归为同一评估事件；历史页默认展示最终尝试，并允许查看其他尝试。
6. 同日不同配置或不同记忆模式属于独立研究观点，不能自动合并。
7. 默认验证周期优先顺序为 20、5、1 个交易日。

## 标的历史页

历史页由静态任务表升级为“结论演化时间轴 + 可展开记录”：

- 时间轴按分析日期和创建时间正序排列；
- 每个节点显示评级、分析日期、评估状态和记忆模式；
- 成功节点绑定 1/5/20 日验证状态；
- 已完成验证直接展示总回报、Alpha、方向正确性和目标价命中状态；
- 最新评级变化以 `旧评级 → 新评级` 显示；
- 历史辅助评估显示引用的来源数量，进入评估详情查看完整来源；
- 失败、取消和技术重试保留审计入口，但视觉上弱化，不参与观点趋势和可靠性统计。

第一阶段不在总览页重复绘制完整 K 线。完整价格回放继续由评估详情页负责，历史页只提供轻量时间轴和验证矩阵，避免信息重复和页面过重。

## API 契约

新增：

```text
GET /api/v1/instrument-overviews
```

支持 ticker、资产类型、运行状态、是否异常、创建日期、游标和 limit 筛选。响应按标的分页，而不是按任务分页，并包含：

- `instrument`：身份字段；
- `latest_run`：最新运行；
- `latest_successful_run` 与 `latest_decision`；
- `previous_rating`；
- `preferred_validation`；
- `validation_stats`：分别按 1/5/20 日统计已成熟样本、命中数和命中率；
- `run_counts`：成功、活动、排队、异常和总数。

扩展：

```text
GET /api/v1/instruments/{ticker}/history
```

将原来的 `validation_outcome: string | null` 替换为结构化 `validations` 数组，并增加记忆模式、引用来源数和尝试归组字段。保留原字段一个兼容周期时，可由后端从首选验证生成简短文本。

REST OpenAPI、TypeScript 类型和 MCP 标的资源必须使用相同结构。

## 后端实现

第一阶段直接基于现有 Instrument、AssessmentRequest、AssessmentRun、Decision、RunConfigSnapshot、Validation 和 MemorySource 关联查询，不新增持久化汇总表。当前规模只有数十条记录，查询投影更简单且不会引入一致性问题。

查询必须避免逐标的 N+1：先分页得到标的集合，再批量读取这些标的的运行、结论和验证记录，在服务层构造稳定响应。为关联和排序复核现有索引；只有缺失时才添加迁移。

当标的或评估规模达到需要度量的性能瓶颈后，再考虑事件驱动的投影表，不在本次提前引入。

## 前端实现

- 总览页用可访问的页签切换“标的台账”和“任务记录”；默认打开标的台账。
- 标的台账保持高密度表格布局，窄屏退化为分组卡片，不使用大面积卡片网格。
- 搜索支持 ticker 和中文名称；标的视图的状态筛选作用于最新运行和未解决异常。
- 标的分页独立于任务分页，切换视图时各自保留游标状态。
- 验证摘要使用纯函数决定首选周期、方向标签、收益格式和样本不足状态，并单独测试。
- 标的历史时间轴使用语义化列表实现，不依赖 Canvas；每个节点可键盘访问对应评估。

## 状态与降级

- 没有成功结论：显示“尚无有效结论”，仍显示最新任务状态。
- 没有成熟验证：显示“待验证”及最近到期时间，不显示准确率。
- 验证失败或行情不可用：显示验证异常，不将其算作方向错误。
- 最新任务失败：保留最近成功结论，同时显示醒目的异常入口。
- 用户缺少 validations:read：隐藏表现数据并显示权限说明，不影响标的台账其他内容。
- 聚合 API 不可用：显示错误提示，用户仍可切换任务记录处理运行问题。

## 测试策略

后端覆盖：

- 同标的多次评估归拢；
- 最新失败不覆盖最新成功结论；
- 首选验证按 20/5/1 选择；
- 未完成和失败验证不进入命中率；
- 同请求重试归组；
- 主体权限与分页隔离；
- OpenAPI 和 MCP 结构一致。

前端覆盖：

- 默认标的台账和任务视图切换；
- 预测—表现配对文字；
- 样本不足、待验证、最新失败和无有效结论；
- 中文名称、ticker、评级变化和计数；
- 历史时间轴顺序、验证矩阵与详情链接；
- 键盘访问、窄屏布局、Lint、类型检查和生产构建。

## 验收标准

- 总览默认只为每个标的展示一行，重复评估不再占据顶层空间。
- 任务记录仍能完整展示全部运行，活动和异常不会被隐藏。
- 每个成熟验证都能明确追溯到具体评估、周期和验证详情。
- 最新结论和最新运行严格区分，失败任务不会覆盖有效结论。
- 历史页按时间顺序展示观点变化及对应 1/5/20 日表现。
- 可靠性统计显示样本数，只计算成熟且有效的验证。
- REST、MCP、前端和 OpenAPI 契约一致。
- 不修改 TradingAgents；全量后端、前端、部署与产物验证通过。
